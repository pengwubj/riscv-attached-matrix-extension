[[programming_model]]
== Programming Model
:imagesdir: ../images

=== Instruction stream

AME instructions are in-line with other instructions on the hart.
They are executed in program order, though follow a weaker memory model than RVWMO such that
AME memory operations are not guaranteed to appear in program order relative to non-AME memory operations
without an ordering fence (see TODO).

[[ame-state-enablement]]
==== AME state enablement

AME adds a two-bit matrix context status field, `MS[1:0]`, to `mstatus`.
The field is shadowed in `sstatus` and is defined analogously to the
vector context status field, `VS[1:0]`.
`MS` controls whether AME state is enabled for the current context and
indicates whether that state might need to be saved during a context switch.

.Encoding of the `MS[1:0]` status field
[cols="1,1,4",options="header"]
|===
|Encoding |Status |Meaning

|0
|Off
|AME state is disabled.

|1
|Initial
|AME state is enabled and should have its architectural initial value.

|2
|Clean
|AME state is enabled and matches the value most recently saved or restored
for the current context.

|3
|Dirty
|AME state is enabled and might have been modified since the last context save.
|===

When an applicable `MS` field is Off, an attempt to execute an AME instruction
other than `ame.acquire` or `ame.release`, or to access an AME CSR other than
`ameown`, raises an illegal-instruction exception. `ame.acquire` reports
`DISABLED`; `ame.release` remains legal.
The Initial, Clean, and Dirty encodings all enable AME execution.

AME context state comprises the `M`, `Acc`, `Md`, and `Ad` register state and
all writable AME CSR state.
The architectural initial state has zero-valued `M` and `Acc` registers,
uninitialized (`0`) `Md` and `Ad` descriptors, and reset-valued writable AME
CSRs.
Writing `MS` does not itself modify AME context state. An `ame.acquire` that
newly grants ownership establishes the initial state before setting `MS` to
Initial.

When `MS` is Initial or Clean, executing an AME instruction other than
`ame.acquire` or `ame.release` that changes, or might change, AME context state
changes `MS` to Dirty.
An implementation may conservatively change `MS` from Initial or Clean to
Dirty even when no AME context state was changed.
Precise dirty-state tracking is therefore an optional optimization for reducing
context-switch overhead.

If `MS` is Dirty, the corresponding `SD` summary bit is set.
After saving AME context state, privileged software may set `MS` to Clean.
On context restore, privileged software either restores a saved context and
sets `MS` to Clean, or establishes the architectural initial state and sets
`MS` to Initial.
At reset, `MS` is Off.
A hart that does not implement AME may make `MS` read-only zero.

When the hypervisor extension is present, `vsstatus` contains an `MS[1:0]`
field with the same encoding.
When `V=1`, both `mstatus.MS` and `vsstatus.MS` are in effect.
Ordinary AME execution is disabled if either field is Off, and an instruction
other than `ame.acquire` or `ame.release` that changes, or might change, AME
context state changes both fields to Dirty.
If `vsstatus.MS` is Dirty, `vsstatus.SD` is set.

=== State

An acquired AME backend binds its AME registers and writable context CSRs to
the current software execution context. The state remains bound until
`ame.release`; see <<shared-ame-backend>>. AME instructions access that bound
state and control data transfer between AME registers and memory.

.Register state and data movement paths for AME. The F/D and V extensions are _optional_ with AME. The only architectural datapath between vector (if present) and AME is through memory. The scalar datapath(s) is/are one-way. AME accumulator state can only be moved to/from the AME matrix registers.
image::ame_state.svg[AME state and architectural datapaths]

The `Acc` registers are used to accumulate the output of partial matrix multiplies.
The `M` registers are general-purpose matrix registers.
They are used for anything that is not an accumulation, including the data operand of load or store instructions,
the input operands of 1D (element-wise/vector) operations, and the output operands of 1D operations.

A single `M` register may hold multiple, one, or part of a square,
depending on implementation-defined parameters and programmed datatype.
Generally, the number of squares that will fit in an `M` register is inversely proportional
to the datatype size (because larger datatypes require more storage).

In contrast, an `Acc` register always holds exactly one square.

=== Squares

The *pack_factor* of a datatype is the number of squares contained in a single M register:

* **Packed** (`sizeof(dtype) < AME_UNIT_DATATYPE_SIZE`): `pack_factor = AME_UNIT_DATATYPE_SIZE / sizeof(dtype)`
* **Unit or Wide** (`sizeof(dtype) >= AME_UNIT_DATATYPE_SIZE`): `pack_factor = 1`

A supported datatype must have an integral storage ratio with
`AME_UNIT_DATATYPE_SIZE`: a packed datatype size must divide the unit size, and
a wide datatype size must be an integer multiple of the unit size.  A datatype
that does not satisfy this rule is reported as unsupported through
`amestatus.UN`.  Consequently the `ceil` in the general group-size formula is
equal to exact division for every supported wide datatype.

When the programmed datatype is a *packed datatype*
(size < `<<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>`),
a single M register holds `pack_factor` logical squares.

The number of elements processed by an AME matrix multiply instruction depends on the datatype.
For non-packed datatypes (`pack_factor = 1`), the operands are `N x N` squares.
When operand formation produces `N_sq > 1`, the input operands span
`N x (N_sq * N)` and `(N_sq * N) x N` elements respectively, while the
accumulator output remains `N x N`.

[NOTE]
--
This constraint keeps the ISA simple: instruction encoding does not need per-operand shape fields
and register mapping is uniform. The accumulator operand always holds exactly one `N x N` square.

For contrast, general matrix multiply on non-square inputs (`M x K` by `K x N`) produces `M x N`.
AME handles this by tiling into squares and zero-padding boundary tiles in software.

.Example (`N = 8`)
* Multiply `A(3x5)` by `B(5x2)`.
* Software packs `A` and `B` into zero-padded `8x8` squares.
* AME computes a full `8x8` result square.
* Software keeps only the valid `3x2` upper-left region and discards padded rows/columns.
+
image::ame-square-padding-example.svg[Matrix padding example for N=8]

Larger non-square problems are handled the same way: process full interior `N x N` tiles normally,
and pad only edge tiles.
--

The row/column dimension, N, is implementation-defined and is equal to the
square root of <<ame:doc:param:AME_NELEM,AME_NELEM>>.
<<ame:doc:param:AME_NELEM,AME_NELEM>> can be any power of 4.

[NOTE]
--
It is possible to create portable AME binaries regardless of the chosen value of
<<ame:doc:param:AME_NELEM,AME_NELEM>>.

Highly-tuned binaries may produce a better result by targeting a specific value of
<<ame:doc:param:AME_NELEM,AME_NELEM>>, similar to how auto-vectorizing compilers can generate
more efficient code for RISC-V Vector when VLEN is known.
--

All elements within a single square have the same datatype, for example unsigned 8-bit integer or
single-precision IEEE floating point.

A single operation may reference squares with different datatypes (for example, 8-bit integer inputs widening to a 16-bit integer output).
Mixed-datatype operations are optional; see <<datatypes>> for the implementation discovery mechanism.

[[mapping-squares-to-m-registers]]
==== Mapping squares to M registers

A single square (vector or matrix) may fit in one `M` register or may span multiple consecutive
`M` registers, depending on the datatype size.
If the datatype is no wider than <<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>,
one register is sufficient;
wider datatypes require additional registers.
The required register count is the datatype size rounded up in units of
<<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>
(that is, `ceil(sizeof(datatype)/AME_UNIT_DATATYPE_SIZE)`).

When a square requires multiple consecutive `M` registers, consecutive registers are combined into a group.
When registers are grouped, the register index must be a multiple of the group size (_e.g._, when
group size is two, register indices must be even).
Specifying a register index that is not a multiple of the group size results in an
Illegal Instruction exception.
This mechanism is analogous to the `LMUL` facility used in the RISC-V vector (`V`) extension.

Packed datatypes can be used directly as operands in compute instructions;
see <<operand-formation>> for how multi-operand instructions determine register spans.

.Square-to-M-register mapping examples
image::ame-square-reg-mapping.svg[Square to M register mapping examples]

When an `M` register is part of a group, only the lowest-indexed register of that group may be used directly in operations.
Using any other register in the group raises an `Illegal Instruction` exception.

// not really bash, but it gets us colored # comments
[source,bash]
----
# precondition:
# a square is in m[2-3]

madd.ew m2, m2, m2  # well-defined, m2 = m2 + m2

madd.ew m2, m3, m3  # raises Illegal Instruction
madd.ew m3, m2, m2  # raises Illegal Instruction
----

[[operand-formation]]
==== Operand formation

When a compute instruction references multiple tensor operands, all operands must contain
the same total number of squares.
The instruction's square count is `N_sq = max(pack_factor)` across all tensor operands.

Each operand's register span is then sized to hold exactly `N_sq` squares:

* **Packed operand** (`pack_factor > 1`): `N_sq / pack_factor` registers
* **Unit or Wide operand** (`pack_factor = 1`): `N_sq x ceil(sizeof(dtype) / AME_UNIT_DATATYPE_SIZE)` registers


Consider an ADD instruction with three tensor operands of different datatypes:

.Operand formation example (`AME_UNIT_DATATYPE_SIZE` = 8 bits)
[cols="1,1,1,1,1",options="header"]
|===
| Operand | Dtype | pack_factor | Register Span | Total Squares

| Tsrc0 | Int4  | 2 | N_sq / 2 = 1 register  | 2
| Tsrc1 | Int8  | 1 | N_sq x 1 = 2 registers | 2
| Tdst  | Int16 | 1 | N_sq x 2 = 4 registers | 2
|===

`N_sq = max(2, 1, 1) = 2` (set by the Int4 operand with `pack_factor = 2`).
All three operands contain `N_sq x AME_NELEM = 2 x AME_NELEM` elements total.

Accumulator (`Acc`) operands are not subject to this rule:
they always hold exactly one square regardless of datatype.

This rule applies uniformly to both 1D (element-wise) and 2D (matrix multiply) instructions.
For 1D instructions, each operand processes `N_sq` squares element-wise — a packed
operand's `pack_factor` squares are stored contiguously in a single register, while a
non-packed operand's `N_sq` squares span `N_sq` registers.
For 2D matrix multiply instructions, the inner product dimension extends to
`N_sq * N` elements; see <<_2_dimensional_matrix_multiply_operations>>.

The conversion-family instructions are explicit exceptions to this general
multi-operand rule.  `mconv.ew` forms the complete expand or compress spans
defined by that instruction, while `mpack.ew.x` and `munpack.ew.x` transfer one
selected logical square and preserve or ignore the other packed slots as
specified.  Their instruction-specific operand-formation rules take
precedence over `N_sq = max(pack_factor)`.

[#norm:ame_nsq_1d]#For an ordinary 1D element-wise instruction, the logical
element count is `N_sq * AME_NELEM`.  The operator is applied to corresponding
logical elements of every operand over that entire range.# An expanded
Operation block whose outer loop is written as `e < AME_NELEM` is shorthand
for this complete range; the register and bit slicing shown in such a block is
replaced by the common logical element read/write builtins.

[#norm:ame_nsq_structural]#A row/column, gather/scatter, prefix, or reduction
instruction applies its documented `N x N` transformation independently to
each of the `N_sq` logical squares.# A row or column index is local to its
square and cannot address another logical square.  An expanded Operation block
that shows only one `N x N` iteration is shorthand for an outer
`sq = 0 .. N_sq-1` loop, with every logical element index offset by
`sq * AME_NELEM`.

[#norm:ame_nsq_matmul]#For a 2D matrix multiply, `K = N_sq * N`.  Operand A is
formed as an `N x K` matrix by placing its logical squares side by side, and
operand B is formed as a `K x N` matrix by stacking its logical squares.  Each
accumulator result remains one `N x N` square.# An expanded Operation block
whose inner loop is written as `j < N` is shorthand for `j < K` with source
elements selected from the corresponding logical square and local coordinate.

==== Operand validation and exception priority

Every encoded `M` or `Md` register specifier is validated with
`<<ame:doc:func:ame_check_m_index,ame_check_m_index>>` immediately after decode
and before any `Md` or `M` state is read.  Thus an index greater than or equal
to `AME_NUM_M_REGS` raises an Illegal Instruction exception even when the
individual instruction's Operation block shows its range check later.

After the required datatypes and operation tuple have been found to be
supported, but before any `M` data access or architectural write, each tensor
operand is formed according to <<operand-formation>>.  Its base, per-square
alignment, and complete physical-register span are then validated with
`<<ame:doc:func:ame_check_m_group,ame_check_m_group>>`.  The complete span,
rather than only the first square's group size, is checked.  A misaligned group
or a group whose final register would be outside the implemented register file
raises an Illegal Instruction exception.

For an instruction that does not use the multi-operand `N_sq` rule, the same
validation applies using the physical span explicitly defined by that
instruction.  Existing per-instruction base and alignment tests are redundant
clarifications of these common checks and do not alter this exception
priority.  An unsupported datatype or operation sets `amestatus.UN` only after
all encoded base indices have passed the first-stage index check; group
alignment and span are not interpreted for an unsupported datatype.

All logical source-element reads in instruction Operation blocks are
semantically calls to
`<<ame:doc:func:ame_read_m_element,ame_read_m_element>>`.  Older expanded
pseudocode that calculates a physical register number and slices the result of
`ame_xform_impl_to_rm(M[base + regno], dtype)` is shorthand for this builtin;
the builtin definition controls if that expansion would transform only part of
a wide square or would otherwise produce an invalid bit index.  In particular,
a wide square is assembled from its complete register group before layout
conversion, and `element_index` is not divided using truncated
`AME_NELEM / group_size` arithmetic.

[[register-group-overlap]]
==== Register group overlap and atomic writeback

Register operands name groups rather than individual storage locations, so two
operands can overlap completely or partially when their datatypes require
different register spans.

[#norm:ame_register_group_overlap]#Unless an instruction explicitly states an
overlap restriction, any source `M` or `Acc` register group may overlap any
destination register group, including complete overlap where the base register
numbers are equal.#

[#norm:ame_source_snapshot]#All source register values, source datatype values,
scalar operands, and index operands are read from the architectural state that
exists immediately before the instruction begins.# Consequently, an
instruction such as a gather, broadcast, shift, or reduction produces the same
result when its destination overlaps a source as it does when the destination
is disjoint.  Pseudocode assignments to a destination do not change the source
snapshot observed by later pseudocode statements.

[#norm:ame_atomic_register_writeback]#For register-only AME instructions, all
destination `M`, `Md`, `Acc`, and `Ad` writes are staged and become visible
together only after every operand, datatype, alignment, bounds, and index check
has completed successfully.#

[#norm:ame_register_exception_atomicity]#If a register-only AME instruction
raises a synchronous exception, none of its staged destination writes commit;
only architectural trap state written by exception handling may change.# An
unsupported datatype or operation is not a synchronous exception: it sets
`amestatus.UN` and returns without committing any destination write, as
described in <<datatypes>>.

An out-of-range gather or scatter index is a synchronous Illegal Instruction
exception, not an unsupported-operation report.  The implementation may
detect it with a preliminary index scan or while evaluating the operation;
either way, the source snapshot and atomic writeback rules require that no
destination register write commits when the exception is raised.

=== Polymorphic instructions

AME instructions do not encode operand datatypes; instead, datatypes are determined by dedicated datatype registers.

[NOTE]
This feature makes AME analogous to polymorphic programming languages
– a single function (instruction) is defined for all datatype combinations (polymorphic argument types).

=== Datatypes

AME supports up to `2^32 - 1` unique datatypes, half of which are reserved for custom use.
The value 0 is reserved to mean uninitialized.

[NOTE]
--
The datatype registers are similar to WARL CSR fields, so implementations only need to support
enough state to represent the datatypes they support.

For example, an implementation that only supports two datatypes would only need two bits to
represent those datatypes plus uninitialized.
--

Standard datatypes and encoding rules are listed in <<datatypes>>.

Implementations may choose which standard datatypes are supported and which custom datatypes
are supported.

A legal implementation may support either zero standard datatypes or zero custom datatypes (i.e.,
all custom or all standard).

[NOTE]
--
Profiles will likely mandate a minimal set of supported datatypes.
--

`M` register datatypes are set using the <<ame:doc:inst:msettyp,msettyp>> instruction and
read using the <<ame:doc:inst:mgettyp,mgettyp>> instruction. `Acc` register datatypes are
set using <<ame:doc:inst:asettyp,asettyp>> and read using
<<ame:doc:inst:agettyp,agettyp>>. Setting an `Acc` datatype with `asettyp` also clears the
corresponding accumulator tile.

=== Data movement

Data movement between AME register files, the integer (X) register file, the floating point (F)
register file, and memory are restricted in order to facilitate a detached AME execution unit.

There are no AME data movement instructions between memory and the `Acc` registers;
rather, `Acc` registers can only be moved in to or out of the `M` registers.

`M` register data can be loaded and stored from/to memory.

A scalar from the X register file can be sent to an `M` register.

AME does not define data movement operations between AME register files and the vector (V)
register file.
Performance-sensitive AME code should use AME 1D operations on matrix data rather than RISC-V Vector.

=== Memory

AME uses the same address space as the host hart.
In systems with virtual memory, AME loads and stores go through (H)S-mode translation and,
if applicable, G-stage translation when run within a hypervisor.

AME provides memory storage variants that operate on one of three memory layouts:

*  Row-major (`mls.rm` / `mss.rm`)
*  Column-major (`mls.cm` / `mss.cm`)
*  Opaque, implementation-defined (`mls` / `mss`)

The row-major and column-major variants are called the _interoperability_ storage instructions.
They transfer data as a contiguous block — no striding or partial-tile predication is supported.

Behavior is only well-defined when loading an opaque tensor layout that was previously stored
opaquely on the same implementation.
Generally, software should assume that loads / stores using the opaque format will be more
performant than loads / stores using one of the formats with a standard layout.

==== Consistency model

Memory transfers from/to `M` registers follow a weaker memory model than other memory transfers on
the hart (from/to the X, F, or V register files).
Informally, memory transfers involving AME state may appear out of program-order with respect to
non-AME memory transfers in the hart.
Ordering is restored with QQQ (fence.ame instruction, ldaq, strl).
`ame.release` additionally completes earlier AME state-save stores before
relinquishing ownership; see <<ame:doc:inst:ame_release,ame.release>>.

=== Operators

AME supports six broad classes of arithmetic and/or logical operators:

*  2D Matrix multiply
*  1D Element-wise/vector
*  Intra-tensor (reduction/expansion/permutation)
*  Register move / data conversion
*  Scalar ingress and data scalar operands
*  Load/store

AME does not support general masking/predication on computational instructions, though a future extension may add support.



==== 2-dimensional matrix multiply operations

AME matrix multiplication instructions calculate the matrix product `C = A x B`.

For *non-packed datatypes* (`pack_factor = 1`), A and B are each a single `N x N` square.
When operand formation produces `N_sq > 1`, A is an `N x (N_sq * N)` matrix
(`N_sq` squares laid side-by-side in the column dimension) and B is an
`(N_sq * N) x N` matrix (`N_sq` squares stacked in the row dimension). The
accumulator output C is always `N x N` regardless of `N_sq`.

Each output element `C[i,j]` is computed as the dot product of:

* row `i` of `A` (length `N_sq * N`), and
* column `j` of `B` (length `N_sq * N`).

The accumulation order for additions inside each dot product is implementation-defined.
That order is fixed within a given implementation, so repeated runs on the same implementation
produce the same result.

The expanded instruction Operation blocks use an ascending inner loop for
readability.  That loop is shorthand for the implementation's fixed
permutation and each step is a call to
`<<ame:doc:func:ame_matmul_accumulate,ame_matmul_accumulate>>`; a `Bits` value
must not be accumulated with raw bit-vector integer addition.

[NOTE]
Different implementations may use different accumulation orders, and therefore may produce
different results (especially for floating-point data).

Formally:

.AME matrix multiplication
[source]
--
def perm(range): implementation-defined permutation over range

# K = N_sq * N, where N_sq is formed across all tensor operands
K = N_sq * N

for i from 0 to N-1:
  for j from 0 to N-1:
    C[i,j] = sum(A[i,k] * B[k,j] for k in perm(0..K-1))
--

Matrix multiplication is not commutative (`A*B != B*A` in general),
so operand order must be preserved by software using AME primitives.

AME defines the matrix-multiply instruction variants listed below.
The destination of matrix multiply operations is always an accumulator register.
The operations differ in
whether or not they accumulate into the destination register (versus overwrite it),
whether or not they transpose an input before multiplying,
and whether or not they negate a result.

[cols="1,2,3",options="header"]
|===
| Instruction   | Operation  | Description
| <<ame:doc:inst:mmul_2d,mmul.2d>>
| `C = A × B`
| Matrix multiply
| <<ame:doc:inst:mmulacc_2d,mmulacc.2d>>
| `C = C + A × B`
| Matrix multiply accumulate
| <<ame:doc:inst:mmulaccneg_2d,mmulaccneg.2d>>
| `C = C - A × B`
| Negated matrix multiply accumulate
| <<ame:doc:inst:mmulat_2d,mmulat.2d>>
| `C = A^T^ × B`
| Matrix multiply with transposed A
| <<ame:doc:inst:mmulatacc_2d,mmulatacc.2d>>
| `C = C + A^T^ × B`

| <<ame:doc:inst:mmulbt_2d,mmulbt.2d>>

==== 1-dimensional elementwise operations

AME defines 1-dimensional (elementwise/vector) operations that use the `M` registers.

Element-wise operations apply the same operator independently at each coordinate of the input squares.
For every position `(i,j)`, the instruction reads `A[i,j]` and `B[i,j]`, computes the result, and
writes it to `C[i,j]`.

There are four classes of elementwise operations: Arithmetic, Bitwise, Comparison, and Nonlinear.

==== Scalars

AME provides an explicit typed scalar ingress instruction and data-scalar
elementwise forms.  Software can therefore use a converted scalar repeatedly
through an M register, or use a data scalar directly without allocating an M
register for it.

===== Scalar ingress and data scalar operands

`mmov.m.x` is the explicit scalar ingress instruction. It interprets an X-register
bit pattern using a datatype encoding supplied in another X register, converts the
value to the destination `Md` datatype with `CONV1D`, and broadcasts the converted
value to every logical element of the destination M operand.

Data scalar `.ew.x` instructions use `CSR[ame_scalar_dtype]` for the source scalar
type. The scalar is converted to the tensor operand datatype before the ordinary
same-datatype operation is evaluated. This keeps the operation support table
polymorphic without requiring a separate mixed-type tuple for every instruction.

Shift amounts, indices, offsets, and other control scalar operands are fixed-type
integer values defined by their instruction. They do not read
`CSR[ame_scalar_dtype]` and do not undergo AME datatype conversion.

==== Load and store

The row-major and column-major interoperability instructions (`mls.rm`, `mls.cm`, `mss.rm`, `mss.cm`)
support both non-packed and packed datatypes. Data is always transferred as a single
contiguous block — no striding, partial-tile, or predicated variants exist.

For *non-packed datatypes* (size >= `AME_UNIT_DATATYPE_SIZE`), one square is transferred
between memory and one (or more, for wide types) M registers.

For *packed datatypes* (size < `AME_UNIT_DATATYPE_SIZE`), `pack_factor` squares are
transferred in a single instruction:

* **Load:** `pack_factor` squares are loaded from contiguous memory and packed into a
  single M register. Each sub-square contains `AME_NELEM` elements.
  In row-major format, the load accesses `sqrt(AME_NELEM)` rows and
  `pack_factor * sqrt(AME_NELEM)` columns in memory, where sub-square `sq` occupies columns
  `sq * sqrt(AME_NELEM)` to `(sq+1) * sqrt(AME_NELEM) - 1`.
  In column-major format, the load accesses `pack_factor * sqrt(AME_NELEM)` rows and
  `sqrt(AME_NELEM)` columns in memory, where sub-square `sq` occupies rows
  `sq * sqrt(AME_NELEM)` to `(sq+1) * sqrt(AME_NELEM) - 1`.

* **Store:** The single packed M register is unpacked and `pack_factor` squares are written
  to contiguous memory using the same layout.

The opaque-format instructions (`mls`, `mss`) transfer exactly one physical M
register without interpreting its datatype.  They are per-register raw
save/restore operations: a wide logical square that occupies multiple M
registers requires one opaque instruction for each physical register.  Packed
sub-squares resident in the selected register are transferred together.
